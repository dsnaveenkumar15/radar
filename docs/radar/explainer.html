How Radar is built

Radar follows the releases of the libraries AI apps are built on and tells you which breaking changes, deprecations and advisories sit between your versions and the latest. An upgrade agent then finds the exact lines in your repository that break, and code checks every finding against the real file before you see it.

The system

Two containers, one database, four outside services

radar-web serves published data, answers Ask Radar and runs the upgrade agent on background threads. radar-batch collects releases, API surfaces and advisories on timers and builds the nightly digest. Both share one SQLite file; published data is immutable releases checked by hash.

  • radar-web pages, Ask Radar, the agent; read-only filesystem
  • radar-batch collectors and the digest on leased jobs
  • SQLite (WAL) releases, API diffs, advisories, agent runs
  • Release store digests and JSON, served only when every hash matches
  • OpenRouter agent models and digest notes
  • Ollama local model and embeddings for Ask Radar
  • GitHub releases for batch; repository snapshots for the agent
  • Sources PyPI, npm, OSV advisories, arXiv, Hacker News, MCP registry

The rule behind every design choice

Models explain, code decides

A model may write a digest note, plan an investigation or draft a patch. Every number, score, version step and finding that reaches a visitor is computed or checked by plain code, so it cannot be talked into a wrong answer by the release notes or source code it is reading.

Signal score

A public formula over source tier, corroboration, star velocity and API evidence. The model never sets it.

API changes

Read from each release's source with ast (Python) and tree-sitter (TypeScript). Never imported, never run.

Agent findings

Kept only if the quoted code is on the cited line of the real file, next to the usage.

Ask Radar

"What broke in X" and "CVEs in X" are answered from data with no model at all.

radar/signal.py: the whole score (shortened)
def score_cluster(items, velocity, has_api_change): tier = 40 * (1.0 if any(i["tier"] == "official" for i in items) else 0.4) corroboration = 20 * min(distinct_sources - 1, 3) / 3 velocity = 20 * min(log10(1 + stars_7d) / log10(1001), 1.0) code = 20 if has_api_change else (12 if a_release_or_repo_backs_it else 0) return min(100, round(tier + corroboration + velocity + code)) # the same formula is published on /sources, versioned as radar.signal@1
The nightly digest

Four collectors, one digest, facts first

Collectors run on timers and feed one database. The nightly digest clusters and scores in code; only then does a model write short notes, which must pass schema and citation checks. Publishing writes a new immutable release and flips CURRENT.

  • collect every 3 h: GitHub releases, arXiv, Hacker News, MCP registry
  • apisurface every 6 h: API snapshot of each new release
  • advisories every 6 h: OSV, which aggregates GitHub advisories
  • apibackfill daily: older releases, 40 downloads a day
  • cluster + score code only
  • notes one model, $0.03 a day cap, schema and citations checked
  • publish new release; old digests are never rewritten

Why publish without a noteThe digest has a deadline and the notes have a daily dollar cap. If the cap closes or the model is down, the computed facts still ship, clearly labelled. A late digest helps nobody; an invented note is worse.
How breaking changes are found

Read the source, never run it

A snapshot per release

Python packages are parsed with ast from their source files; npm packages from their .d.ts files with tree-sitter. Nothing is imported or executed. A daily backfill covers about two years of older minor releases, 40 downloads at a time.

A diff between neighbours

Removed, changed and deprecated public symbols, plus "moved": langgraph.prebuilt now lives in the langgraph-prebuilt package, which langgraph installs, so the import still works and it is reported as notable, not breaking.

Measured

The diff evaluation runs 22 labelled cases: precision 1.00, recall 1.00 (the gate is 0.9 and 0.8).

The upgrade agent

Eight nodes, three of them a model

A LangGraph state graph. Fetching, parsing, grounding against Radar's recorded changes, indexing usages, verifying and computing the upgrade path are plain Python; only plan, investigate and the report text use a model. The dashed links are the early exits.

  • fetch_inputs public repo snapshot or a pasted file
  • parse_deps requirements, pyproject, package.json, lock files
  • ground your versions against Radar's recorded changes
  • index_code Python and TypeScript usages of changed symbols
  • plan model orders up to 8 candidates
  • investigate model loop with read-only tools, 30 calls max
  • verify code checks every quote against the file
  • report patch and summary by model; path and difficulty by code

What the model did

Ordered the one candidate, called four read-only tools, confirmed the break and wrote the patch and summary.

What code did

Fetched the snapshot, found the dependency and its 874 recorded changes, located the usage at line 8, checked the quote against the real file, and computed the upgrade path: 9 version steps, difficulty Easy, about 0.75 hours, 1 file.

Three models, by roleGLM-5.3 Flash planned and wrote the report; DeepSeek V4.1 Flash and a free Nemotron model investigated. The free model is added only for public-repository runs, so a pasted file never reaches it.
The gate between the model and the visitor

A finding counts only if its quote is on the line

radar/agent/verify.py (shortened)
def _check(finding, files, candidates): if finding.verdict != "confirmed": return "not a confirmed finding" if finding.candidate not in candidates: return "refers to no known candidate" for ev in finding.evidence: if ev.path not in files: return "not in the snapshot" if ev.line not in range(1, len(lines)+1): return "line does not exist" if len(quote) < 6 or quote not in line_text: return "the quote is not on that line" if no evidence from the candidate's own file: return "no evidence from the candidate's file" if no evidence within 3 lines of the usage: return "no evidence near the usage" return "" # verified

What it rules out

A finding about a file the agent never fetched, a line that does not exist, a paraphrased quote, a quote from some other file, or evidence far from the usage the candidate was about. Paths are normalised, so ../ tricks fail too.

What it does not decide

Whether the patch is right. The report says patches are suggestions to check against the listed API changes, and the verifier only proves the model looked at the real code.

MeasuredThe offline agent evaluation runs 8 fixture repositories, including a hostile one: precision 1.0, recall 0.833, $0 (scripted models). The gate is 0.9 and 0.8.

What the report hands over

A summary, the gaps it could not check, a unified diff per finding, the whole patch as a .diff file, and an issue in Markdown ready to paste into GitHub.

Two tools that need no model, or no upload

Answers from data, checks in your browser

Ask Radar

Structured questions ("what broke in X", "CVEs in X") are answered from the API-diff and advisory data, and the answer says so: "Answered from API-diff and advisory data; no model was involved."

Open questions search the archive with embeddings and a local model on the Docker network answers, every sentence citing a real item. Without Ollama, data answers still work.

Limits

10 questions a minute per address, with a small burst. Release notes are untrusted text: fenced and labelled in every prompt.

Upgrade report

A pasted dependency file is read in the browser and compared with the published upgrade.json there. The file is never sent to the server.

"My stack" and "since last visit"

Kept in the visitor's browser only. Radar stores nothing about what you use.

WhyThe cheapest, safest model call is the one you do not make. Most questions people ask about upgrades have exact answers in the data.
Cost and safety controls

Every agent run has a hard ceiling

The agent shares the gateway from the common core: the run budget is checked before every model call. Radar adds a time reserve, so a run that spends its investigation time still writes a report.

Defence in layers

Four layers, each with its own guard

Loading the 3D view.
Top = closest to the visitor · white dot = reply · slide 2 has every link

Edge

TLS, HSTS for a year, strict CSP with no inline code, frame-ancestors 'none'. Per-IP limits: Ask Radar 10 a minute, error reports 5 a minute, agent runs per day.

App

Non-root, read-only root filesystem, all Linux capabilities dropped, no-new-privileges, CPU and memory limits, and a concurrency gate.

Data

SQLite in WAL mode with a nightly backup. Releases carry a SHA-256 manifest and web refuses a file whose hash does not match. A published digest is never rewritten; corrections are errata.

External

OpenRouter with data collection denied, except one free model allowed only for public-repository runs, never for pasted files. Ollama only on the Docker network. GitHub through a token that can only read public code.

Failure, testing and operations

Built to fail in a known way

When something breaks

  • A source fails: source health on /sources; below 80% of official sources the digest is labelled "partial".
  • Daily cap or model outage: facts published, notes "unsynthesized".
  • A crash restarts the container; leased jobs return; agent runs in flight are marked failed.
  • A bad release fails its hash check; the worker's silence trips the uptime monitor in about 30 minutes.

How it is tested

  • 862 tests in 91 files on every push; models are scripted fakes.
  • Diff evaluation: 22 cases, precision 1.00, recall 1.00.
  • Agent evaluation: 8 fixture repositories, precision 1.0, recall 0.833; a live run with real models before a deploy.
  • Every bug fix starts with a failing test.

How it is deployed

  • Recent releases: a data-volume backup and a git tag first.
  • Fast-forward-only pull; a failed build keeps the old containers running.
  • A health wait that goes back to the old commit if web is not healthy.
  • A runbook in Simplified Technical English: one instruction per step.
